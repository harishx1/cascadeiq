      Why this is not a static demo

      The prediction engine has no idea what your services do. It receives a directed graph of nodes and edges plus six universally observable signals — latency, error rate, throughput, CPU, memory, queue depth — and nothing else. Add a node, delete a node, import a topology from JSON: the same code path runs, unchanged.

      Failure modes are protocol-level, not application-level: a broken dependency, a saturated resource, a lapsed credential. Those exist in every stack regardless of language or framework.

      How it scales

      • Graph algorithms are O(V+E); a 300-node mesh runs in ~14 ms per tick.
      • Simulation is event-driven with an heapq schedule, not a fixed grid.
      • Log ingestion and prediction are separate passes over an interface — in production the generator is swapped for a real log pipeline (Loki / Elasticsearch) with no change downstream.
      • State broadcast is delta-encoded, so bandwidth is independent of log volume.

      Model stack

      1. Propagation model — dependency-weighted pressure with a dead-dependency tipping point and protocol-specific damping.
      2. Root-cause isolation — first-anomaly onset ranking combined with reachability over the failure-direction subgraph.
      3. Forecast — per-node risk aggregation with breaker / rate-limit corrections, mapped to a failure probability and ETA.
      4. Recovery ranking — strategy × fault-class × node-role match scored against success, risk, blast radius and time-to-recover.
